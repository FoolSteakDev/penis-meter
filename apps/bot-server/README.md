# bot-server

## Режим гравця

Кожен гравець має `mode`: `'grow'` (🍆 Ростити хуй, дефолт) або `'drill'` (🕳 Бурити скважину).
Перемикається кнопкою в `/status`, з кулдауном `MODE_SWITCH_COOLDOWN_HOURS` (24 год,
`src/config/constants.ts`) між перемиканнями.

Для буровика **кожна дельта дзеркалиться** (`delta × (-1)`) — і в `/metr`, і в дуелях
(`src/utils/mode.util.ts::modeSign`). Критичний провал для буровика - удача (значення йде
глибше в мінус), критичний успіх - невдача. Це стосується як власного виміру, так і обох
сторін дуелі (виграна дуель проти гравця в `grow` теж штовхає буровика глибше).

Рейтинг - **один спільний**, за `|value|`: буровик на −500 стоїть поруч із гравцем на +500
(`src/services/user.service.ts::getChatRating/getGlobalRating`, MongoDB-агрегейт із `$abs`).
Місця в топі сезону/раунду (`getGrowthRank`) і "найбільший стрибок"/MVP тижня
(`round-processor.service.ts`) рахуються за **прогресом** (`progress(value, mode)`) - скільки
гравець просунувся в бік ВЛАСНОЇ мети, а не за сирим значенням.

## Перевірка чесності дуелей

Дуель вирішується чистою функцією `challengerWinsCoinFlip` (`src/utils/duel-coin.util.ts`) —
`Math.random() < 0.5`, без залежності від ролі, ставки чи value. Чесність кидка доведена
юніт-тестом на 200 000 симуляцій (`src/utils/duel-coin.util.test.ts`).

Щоб перевірити реальну БД, а не лише синтетичний тест, запусти:

```
npm run duel:stats -w apps/bot-server
```

Скрипт (`src/scripts/duel-stats.ts`) читає всю `duel-history`, друкує загальний win-rate
ініціатора, розбивку по гравцях (>= 20 дуелей) і перевірку на асиметрію ролі
(ініціатор vs ціль), кожен раз із двостороннім p-value (H₀: p=0.5, нормальна апроксимація
з поправкою на неперервність, `src/utils/stats.util.ts`).

**Що вважати аномалією:** `p < 0.01` **і** `n > 300`. Менші вибірки й помірні p — це шум,
не сигнал (див. код-план `PLAN-actor-labels-duel-audit-drill-mode.md`, розділ 2.1).

## Межа 0 і зміна режиму

Інваріант: `mode === 'grow' → value >= 0`, `mode === 'drill' → value <= 0` (нуль валідний в
обох). Тримається клампом на **кожному** записі value — атомарний `findOneAndUpdate` з
aggregation pipeline (`src/utils/value-update.util.ts::buildClampedValueUpdate`), а не
`$inc`: кламп рахується на сервері від поточного `$value`, інакше паралельний `/metr` і
дуель над тим самим юзером розʼїхали б value і growth. Growth-поля (`season_growth`,
`round_growth`, `round_best_delta`) синхронізуються ФАКТИЧНО застосованою величиною, а не
заявленою — якщо кидок уперся в межу, до приросту йде лише те, що реально пройшло.

`/metr` і результат дуелі показують, коли спрацював кламп (`outcome.clamped`,
`loserApplied < amount`), а не мовчать про урізану дельту.

**Зміна режиму обнуляє value, якщо знак не збігається** з новим режимом (`grow → drill` при
додатному value чи навпаки). Перемикання — двокрокове: `/status` показує екран
підтвердження з точною сумою, що згорить, і лише друге натискання пише в БД
(`bot/commands/mode.command.ts`). Спалене **віднімається** від `season_growth`/
`round_growth` (не додається) — інакше гравець отримував би нагороду за власне спалення.
Кулдаун (`MODE_SWITCH_COOLDOWN_HOURS`) перевіряється на обох кроках.

Дуель для гравця з прогресом `< 1` (впритул до 0) **заборонена** — `getStakeBounds` більше
не має фіксованої стелі-фолбеку на не-позитивний прогрес: із клампом вона була б дірою
(програш нічого не коштує, виграш необмежений).

Гравці, у яких value набрало "чужий" знак ще до появи інваріанту, виправляються одноразовим
ідемпотентним скриптом:

```
npm run backfill:mode-sign -w apps/bot-server           # dry-run, нічого не пише
npm run backfill:mode-sign -w apps/bot-server -- --apply
```

Обнуляє лише value, **growth-поля не чіпає** — це не свідомий вибір гравця (як при
перемиканні режиму), а виправлення стану, що виник до інваріанту.

Адмінка (`/users`) дозволяє редагувати `mode` окремо, з валідацією пари: якщо результівний
знак value суперечить обраному режиму — `400`, значення не клампиться мовчки.
